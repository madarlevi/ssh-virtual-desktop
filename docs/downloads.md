# Browser request capture and remote execution

## Data flow and trust

The native child WebView2 renders on Windows. WebView2/Tauri download interception cancels the normal local save. Only request metadata and progress cross SSH; the Linux downloader fetches the response body itself. A browser may receive response headers and some network-buffered bytes before interception, so this is not a promise of zero browser traffic.

`browser_requests.rs` uses the documented `ICoreWebView2_2::add_WebResourceResponseReceived` API. It inspects the committed request headers/method/URI and response Content-Disposition/Content-Length, never response bodies. Candidate attachment/application responses are retained in a bounded native vault (32 recent requests, five seconds; 32 offered requests, 10 minutes, purged every 30 seconds). HTML/JSON responses without download disposition are not captured. Tauri's DownloadStarting wrapper supplies the final download URL and suggested filename; matching is per browser and exact URL, only when exactly one fresh candidate matches. Download interception waits up to one second for the separate native response event; ambiguous/stale or absent metadata requires a manual request instead of guessing. Redirect chains are not reconstructed; the captured request is the final observed browser request.

Cookies are limited to those in that committed request's Cookie header, selected by WebView2 for the request's domain, path, transport and cookie attributes. No cookie database is copied. HttpOnly values stay native. WebView2 may omit headers or body data in some contexts. Missing cookies/Authorization cannot be inferred. Missing context requires explicitly confirming a direct GET or recreating the request manually; a known unavailable POST body is blocked.

For POST, only a cloneable/seekable request `IStream` with a known complete size at most 1 MiB is captured. Reading occurs on the clone, never consuming the browser's stream. Bodies that cannot be cloned/read completely are marked unavailable. Multipart binary bodies can work only if fully captured with their corresponding Content-Type/boundary; manual entry supports UTF-8 text/form/JSON only. A POST has already been sent by the browser; replay sends it again and may repeat server-side effects. Do not replay non-idempotent forms unless you understand that effect.

## Consent and serialization

The frontend receives header names/counts, method, body byte count and authentication/cookie indicators, never captured cookie or header values. Manual fields are hidden until requested. Every dialog starts with authentication consent unchecked. Without consent only Accept, Accept-Language, User-Agent, Content-Type and Origin are eligible; Cookie, Authorization, Referer and custom headers are omitted. POST requires approval. Sensitive forwarding requires HTTPS. Changing the URL invalidates captured context. There is no browser JavaScript bridge into the vault.

Host, connection/transfer headers, compression negotiation, conditional/range headers, proxy authentication and `Sec-*` headers are not forwarded. Content-Length is generated by curl. Accept-Encoding is negotiated as identity for compatibility; original compression headers are not copied. Header values reject controls/CRLF, names must be HTTP tokens, headers total at most 64 KiB/64 entries. Secrets are serialized as curl configuration (with its own escaping) and body files, not shell arguments. All shell-controlled paths use POSIX quoting.

Plain GET chooses aria2c, wget, then curl. Header-bearing requests and POST require curl. The server is never modified by installing tools. Requests are transferred over SFTP into a private UUID directory with mode 0700 and files 0600. curl is launched with `--disable --config PATH` to ignore user curl configuration. Request values never appear in process arguments or application logs. Worker exit/cancel removes the temporary request files. Only minimal non-secret request characteristics are in persistent job metadata; the URL itself may contain a token and is kept privately for history/retry.

## Redirects, retries and lifetime

Public GET can follow up to ten redirects and retry bounded transient failures. Credential-bearing and POST requests never follow a redirect, even within the same origin. A 3xx response fails with instructions to open the target in the browser, capture a new request, and approve again. This deliberately avoids automatic cross-origin disclosure or implicit POST-to-GET conversion. Server-origin allowlists/interactive redirect continuation are future work.

Plain GET Retry starts a new job; credential/body/header requests require recapture and renewed approval. POST is never automatically retried. Partial-file resume across separate jobs is not implemented: validators, expired tokens and changed objects must be handled before it can be promised safely. Cancellation removes the partial file. No local-download/upload fallback is implemented or selected silently. Blob/data URLs, browser-generated files, service-worker-only state, client certificates, browser/IP-bound sessions and anti-bot checks may not be delegable.

Jobs use `nohup setsid sh` and survive client disconnect where server policy permits; no permanent daemon or public RPC port is installed. They do not survive reboot or policies killing user processes. SIGKILL/server failures can prevent trap cleanup: inspect/remove stale request material and destination locks in the private job directory only after confirming the worker ended. Root/the server account can read approved credentials during execution; forward only to a trusted server.

Progress is actual SFTP partial-file size, sampled every two seconds while the manager is displayed. Speed is derived from byte samples; size/percentage are only shown when a usable size was observed or at completion. Captured sizes can change on replay. Atomic same-directory hard-link publication prevents overwrites. Cancellation markers avoid killing unrelated stale PIDs.
